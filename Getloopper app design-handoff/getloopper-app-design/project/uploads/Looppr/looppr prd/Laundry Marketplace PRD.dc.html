Product Requirements Document · v1.0 · July 2026

Laundry Marketplace Platform

A two-sided marketplace connecting Clients with independent LaundryMart vendors for on-demand wash, fold, and delivery service.

Prepared for: Engineering, Design, QA, DevOps & Product · Status: Ready for implementation

1. Executive Summary

This document specifies a production-ready, two-sided marketplace web application built on the MERN stack (MongoDB, Express, React, Node.js). The platform has exactly two user roles for MVP — Client (customer) and LaundryMart (vendor) — with no administrative panel. Clients discover nearby LaundryMarts using geolocation search, compare services and pricing, schedule pickup and delivery, pay securely online, and track orders in real time. LaundryMarts manage their business profile, service catalog, pricing, and incoming orders through a dedicated dashboard.

The document below is organized as the single source of truth for the project: it covers product scope, every frontend screen with its states and validation rules, the complete backend architecture and database schema, the full REST API surface, the reusable UI component library, core user flows, security and testing strategy, and a phased delivery roadmap. Each functional requirement includes business logic, validation rules, acceptance criteria, and edge cases so that no team needs additional clarification to begin building.

2. Product Vision & Scope

2.1 Vision

Make professional laundry service as easy to book as a rideshare: find a trusted local LaundryMart, schedule a pickup in under a minute, and track the order until clean laundry is back at the door — with transparent, itemized pricing on both sides of the marketplace.

2.2 In Scope (MVP)

  • Client and LaundryMart authentication, each with its own dashboard
  • Geolocation-based vendor search, filtering, and sorting
  • Vendor service catalogs with per-item pricing set by the vendor
  • Booking, scheduled pickup/delivery windows, and checkout with online payment
  • Order lifecycle management and live status tracking for both roles
  • Ratings & reviews, notifications, and profile/business settings

2.3 Out of Scope (MVP)

  • Admin panel / internal ops console (flagged for Phase 2 — see §20)
  • Native mobile apps (responsive web only for MVP)
  • In-app driver/logistics fleet management (pickup/delivery is arranged by the LaundryMart itself in MVP)
  • Multi-currency support, subscriptions/recurring billing, loyalty programs

4. Payment Gateway: Stripe vs. Flutterwave

Recommendation: Stripe.

Criteria Stripe Flutterwave
Marketplace payoutsStripe Connect natively splits a payment between platform fee and vendor payout, with vendor onboarding (KYC) built in.Sub-account/split payment support exists but is less mature for automated marketplace payouts.
Docs & SDKsBest-in-class Node.js SDK, Elements for PCI-compliant card capture, extensive test tooling.Solid SDK, smaller ecosystem, fewer pre-built UI primitives.
Geographic fitStrongest in US/EU/UK markets.Strongest in Africa; not the target launch geography here.

Given the target markets (US launch cities), Stripe is the better fit — primarily because of Stripe Connect, which is purpose-built for exactly this app's shape: a platform that collects payment from a Client and pays out a percentage to a LaundryMart vendor.

4.1 Integration Workflow

  1. Vendor onboarding: On business registration, create a Stripe Connect Express account for the LaundryMart (stripe.accounts.create({'{'} type: 'express' {'}'})); redirect to Stripe-hosted onboarding link to collect KYC/bank details. Store stripeAccountId on the Vendor document.
  2. Checkout: Client submits card via Stripe Elements (client-side tokenization; raw card data never hits our API). Frontend sends the resulting paymentMethodId to POST /api/payments/create-intent.
  3. PaymentIntent with destination charge: Backend creates a PaymentIntent with application_fee_amount (platform commission, default 15%) and transfer_data.destination set to the vendor's connected account ID — Stripe splits funds automatically at settlement.
  4. Confirmation: Client confirms via stripe.confirmCardPayment; on success the Order status moves from pending_payment → confirmed.
  5. Webhooks (source of truth): Listen for payment_intent.succeeded, payment_intent.payment_failed, and account.updated at POST /api/webhooks/stripe; verify signature with the webhook secret before trusting the payload. Never mark an order paid from the client-side confirmation alone.
  6. Refunds: Triggered from an order cancellation within the cancellation window (§9); calls stripe.refunds.create with reverse_transfer: true to claw back the vendor's portion too.

5. User Roles & Authentication

Exactly two roles for MVP: Client and LaundryMart. No admin role. Role is stored on the User document (role: 'client' | 'vendor') and encoded in the JWT payload; middleware checks it on every protected route (RBAC, §14).

5.1 Client Authentication Flow

  1. Sign Up: name, email, phone, password, confirm password. Validation: email format + uniqueness check (async, on blur); password ≥ 8 chars with 1 number + 1 letter; phone via libphonenumber pattern. On submit: POST /api/auth/client/register hashes password (bcrypt, 12 rounds), creates User, sends verification email, returns access+refresh tokens. Edge case: duplicate email returns 409 with a field-level error, not a generic toast.
  2. Login: email + password → POST /api/auth/client/login. Rate-limited to 5 attempts / 15 min per IP+email pair; on the 6th, respond 429 with retry-after.
  3. Forgot Password: email → POST /api/auth/forgot-password issues a signed, single-use reset token (JWT, 1-hour expiry) emailed as a link. Always returns 200 (never reveal whether the email exists).
  4. Reset Password: token + new password → POST /api/auth/reset-password verifies token signature + expiry + single-use flag, updates password hash, invalidates all existing refresh tokens for that user.
  5. Logout: POST /api/auth/logout clears the httpOnly refresh cookie and blacklists the refresh token server-side.

5.2 LaundryMart Authentication Flow

  1. Register Business: multi-step form — (1) owner name, email, phone, password; (2) business name, address (geocoded to lat/lng via Google Geocoding API), business hours; (3) Stripe Connect onboarding redirect. Vendor record is created with status: 'pending_verification' until Stripe onboarding completes (webhook flips it to active) — a pending vendor is not shown in client search results.
  2. Login / Forgot / Reset / Logout: identical mechanics to Client flows above, on vendor-scoped routes (/api/auth/vendor/*) so tokens are minted with role: 'vendor'.

Acceptance criteria (both roles): a successful auth call returns a user/vendor object (no password hash), sets the refresh token as httpOnly+Secure+SameSite=Lax, and the access token in the response body for the client to hold in memory (never localStorage, to reduce XSS token theft surface).

10. Functional Requirements & Business Rules

10.1 Order Lifecycle (Business Logic)

Order status enum: pending_payment → confirmed → accepted → picked_up → in_progress → ready_for_delivery → delivered → completed, with terminal branches cancelled and disputed.

  • Acceptance window: a vendor has 15 minutes to accept or reject a new order; if it times out, the order auto-cancels and the Client is refunded in full and prompted to rebook with another vendor.
  • Cancellation policy: Client may cancel free of charge up until the vendor marks picked_up; after that, a cancellation requires vendor approval and may incur a partial charge for work already done.
  • Reviews: only enabled on orders in completed status, one review per order, editable within 48 hours of submission.
  • Platform fee: default 15% commission on order subtotal (configurable per-vendor field for future negotiated rates), computed server-side — never trust a client-submitted total.
  • Geosearch radius: default 8 miles, user-adjustable up to 25 miles; vendors beyond that are excluded from results regardless of rating.

10.2 Client Features

  • Register/login, geolocation vendor search with filter/sort, vendor profile comparison
  • Schedule pickup/delivery, place orders, pay securely, track live status, view order history
  • Rate & review completed orders, manage notifications and profile

10.3 LaundryMart Features

  • Register business, manage profile + logo/gallery uploads, manage services and pricing
  • Accept/reject orders, update order status through the lifecycle, view earnings and payouts
  • Respond to customer requests, manage notifications

11. Backend Architecture

11.1 System Overview

A layered Express application: routes declare endpoints and attach validators/middleware → controllers parse the request and call services (business logic, framework-agnostic) → services talk to Mongoose models. Cross-cutting concerns (auth, error handling, logging, rate limiting) live in middleware applied globally or per-router.

15. Core User Flows

15.1 Client: Search → Book → Pay → Track

Landing → grant/deny geolocation → Nearby LaundryMarts (list+map) → apply filters → open Vendor Details → Book Laundry Service (select items) → Schedule Pickup (date/time/address) → Checkout (review totals, add tip/promo) → Payment (Stripe Element, 3DS if required) → Order confirmed → Order Tracking (live timeline) → Delivered → prompted to Leave Review.

15.2 Vendor: Registration → First Order

Register Business (3-step) → Stripe Connect onboarding (external redirect + return) → status flips to active on webhook → add ≥1 Service → set Availability → appears in Client search → receives New Order notification → Accept within 15-min window → update status through pickup/in-progress/ready/delivered → Earnings updates on webhook-confirmed payout.

15.3 Order Cancellation

Client or Vendor initiates cancel → system checks current status against cutoff (§10.1) → if before pickup: auto full refund via Stripe (reverse_transfer:true), order → cancelled, both parties notified → if after pickup: requires Vendor approval of a partial refund amount before the refund fires.

16. Security Requirements

  • JWT: short-lived access token (15 min) in memory; refresh token (30 days) as httpOnly+Secure+SameSite=Lax cookie; refresh rotation with reuse detection (a reused refresh token revokes the whole family).
  • Password hashing: bcrypt, 12 salt rounds; never log or return password hashes (select:false on schema).
  • RBAC: middleware reads req.user.role from verified JWT; route-level requireRole('vendor') guards; resource-level ownership checks (e.g. a vendor can only PATCH their own Service/Order).
  • Input validation: express-validator chains on every mutating route; reject unknown fields; sanitize/escape free-text fields (review comments, order instructions) before storage.
  • File uploads: Multer memory storage, 5MB limit, MIME allowlist (jpg/png/webp), re-encode via Cloudinary (strips EXIF/GPS metadata automatically).
  • Rate limiting: global 100 req/min/IP; stricter 5 req/15min on auth endpoints; keyed by IP+identifier to prevent credential-stuffing.
  • NoSQL injection: Mongoose schema typing rejects operator-shaped input by default; additionally strip $/.-prefixed keys from all request bodies via sanitization middleware.
  • XSS: React's default escaping + Content-Security-Policy header; never dangerouslySetInnerHTML on user-supplied text.
  • CSRF: SameSite=Lax cookie + custom header requirement on state-changing requests mitigates CSRF without a separate token scheme.
  • CORS: allowlist the production frontend origin only; credentials:true for cookie-based refresh.
  • Secrets: all keys (Stripe, Cloudinary, JWT secret, Mongo URI) in environment variables, never committed; separate test/live Stripe keys per environment.

18. Deployment

  • Frontend: Vercel, auto-deploy on merge to main, preview deployments per PR.
  • Backend: Render or Railway, containerized Node service; health-check endpoint /api/health.
  • Database: MongoDB Atlas, M10+ cluster with automated daily backups and point-in-time recovery.
  • Images: Cloudinary, auto-format/quality (f_auto,q_auto) delivery.
  • Domain: apex + www on Vercel; api. subdomain pointed at the backend host.
  • Env vars: managed per-environment in each platform's secret store; never in source control.
  • CI/CD: GitHub Actions — lint → unit/integration tests → Newman API tests → build → deploy; block merge on red pipeline.
  • Monitoring/Logging: Sentry for frontend+backend error tracking; structured JSON logs (Winston/Pino) shipped to the hosting platform's log stream; Stripe Dashboard + webhook delivery logs monitored for failed events.

19. Non-Functional Requirements

  • Performance: geo-search API p95 < 400ms; dashboard pages first-contentful-paint < 1.5s on 4G.
  • Availability: 99.5% uptime target for API; graceful degradation (cached last-known vendor list) if geo-search is briefly unavailable.
  • Scalability: stateless API instances behind the host's load balancer; MongoDB indexes reviewed at 100k+ orders.
  • Accessibility: WCAG 2.1 AA — keyboard navigable, focus-visible states, form errors announced via aria-live.
  • Responsiveness: full functionality at 320px–2560px; dashboards use a collapsible sidebar < 1024px.

20. Assumptions, Risks & Dependencies

Assumptions

  • Pickup/delivery logistics are handled by each LaundryMart itself (own staff/couriers) — the platform does not dispatch drivers in MVP.
  • Single currency (USD) and single-region (US) launch; tax calculated as a flat configurable rate, not full nexus-based tax compliance.
  • Vendors are individually vetted/onboarded manually before their Stripe Connect account is approved for payouts (Stripe's own risk review).

Risks

  • No admin panel in MVP means disputes/fraud require direct database intervention — mitigate with a minimal internal read-only ops view before public launch if order volume is non-trivial.
  • Vendor-managed logistics means delivery time reliability varies by vendor — surfaced to Clients via the vendor's rating/turnaround stats rather than a platform guarantee.
  • Stripe Connect Express onboarding drop-off could bottleneck vendor supply — track completion rate and add reminder emails.

Dependencies

  • Google Geocoding/Places API key (address entry + geocoding)
  • Stripe account (Connect enabled) with live + test keys
  • Cloudinary account for media storage
  • Transactional email provider (e.g. SendGrid/Postmark) for auth + notification emails
